# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The Vite/React/TypeScript app lives in the `bicycle forum/` subdirectory (not the repo root) — run all commands from there:

```
cd "bicycle forum"
npm run dev       # start the Vite dev server
npm run build     # type-check (tsc -b) then production build
npm run lint      # eslint .
npm run preview   # preview the production build locally
npm run test      # vitest run - single pass, used before committing
npm run test:watch  # vitest - watch mode for local iteration
```

Tests are Vitest + React Testing Library, `*.test.ts`/`*.test.tsx` files sitting next to the source they cover (e.g. `src/lib/posts.test.ts`, `src/pages/Login/Login.test.tsx`) rather than in a separate `__tests__` tree. `vitest.config.ts` runs them under jsdom via `src/test/setup.ts` (jest-dom matchers, a `matchMedia` stub) and leaves CSS imports stubbed out rather than actually parsed - jsdom's CSS parser chokes on some of this app's syntax, which silently broke accessible-name computation for one element early on; nothing here asserts on computed styles anyway. `.env.test` supplies dummy `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` so `supabaseClient.ts` doesn't throw at import time - no test ever hits a real network/DB. `src/test/mockSupabase.ts`'s `QueryBuilderMock` stands in for supabase-js's chainable, thenable query/RPC builders (every lib/*.ts function is mocked at the `supabase.from()`/`.rpc()` level via `vi.mock('.../supabaseClient', async () => { const { createSupabaseMock } = await import('.../test/mockSupabase'); return { supabase: createSupabaseMock() } })` - the dynamic `import()` inside the factory sidesteps the hoisting TDZ issue a plain closed-over variable would hit), and `src/test/testUtils.tsx`'s `renderWithProviders()`/`makeProfile()`/`makeSignedInAuthValue()` wrap a component tree in the same Auth/Theme/Router context providers `App.tsx` composes at the root. Coverage prioritizes high-value flows over exhaustiveness (every lib/*.ts module, the shared components, and every page now has a test), rather than covering every exported function/branch/prop-combination within them - e.g. `AvatarCropper`'s own canvas/pointer-drag geometry has no dedicated test and is stubbed out (via its imperative handle) in `Profile.test.tsx`, since jsdom can't meaningfully exercise real image-load/canvas behavior.

Supabase is set up: the client lives at `src/lib/supabaseClient.ts` (reads `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` from `.env.local` — copy `.env.example` to get started), generated row/table types are in `src/lib/database.types.ts`, and the schema lives in `supabase/migrations/01`–`34` (profiles/auth wiring, posts+comments, tags, badges, votes+reputation, hardening passes, an `avatars` Storage bucket, `posts.dislike_count`, `search_posts()`, comment replies, immutability guards on posts/comments' identity fields now that both are editable, a self-service `delete_own_account()` RPC, a `saved_posts` bookmarks table, a profile bio, a `post-images` Storage bucket, a `post_images` child table - up to 5 rows per post - that replaced migration 30's single `posts.image_url` column, an admin-inclusive delete policy on that bucket so cleanup works when an admin deletes someone else's post, a `notifications` table populated entirely by a trigger on `comments` insert, and (migration 34) a `comments.reply_target_id` column plus tighter notification/mention-regex handling from a code-review pass - see the Notifications entry below). Apply new migrations with the Supabase MCP tools (`apply_migration` against the project, then mirror the same SQL into a new numbered file here) rather than hand-editing the live schema; regenerate `database.types.ts` via `generate_typescript_types` after any schema change instead of hand-editing it. A migration that tightens a `check` constraint on a column already receiving writes (e.g. `29_bio_max_256.sql` lowering `profiles.bio`'s cap) should add it `not valid` and follow up with a separate `validate constraint`, so the `alter table` itself doesn't block on scanning/rejecting rows that are already out of the new, narrower bound - safe to skip only when the column genuinely has no real data yet to violate it, as was true there.

## Testing new features

Every new feature (new lib functions, components, pages, or user-facing flows) must ship with tests in the same piece of work — not as a follow-up requested separately. Use the existing Vitest + React Testing Library infrastructure described above and in `src/test/` (the Supabase query-builder mock, the provider-wrapped render helpers, co-located `*.test.ts(x)` files) rather than inventing a new pattern.

## Commit hygiene

Commit finished, working increments of the forum with clear, descriptive commit messages (not just at the end of a session) and push them, so `origin/main` always has a recent, working saved version of the project to fall back to. Verify `npm run lint` and `npm run build` pass before committing.

## Intended architecture (from Requirements.md)

The project is meant to be a **TypeScript + React + Vite** bicycle forum, branded **Slipstream** (`index.html`'s title, the navbar's `#brand`, and `package.json`'s `name` all reflect this), with **Supabase** as the backing store and for authentication. Do not build a custom auth entity — Supabase auth is the system of record for login/session state.

Key domain entities and rules to preserve when implementing data models and validation:

- **User**: first name (4–32 chars) + optional last name (4–32 chars when given), email (valid, unique) and/or username. Username is set at registration and immutable afterward; an optional profile photo is stored in the `avatars` Storage bucket (public read, owner-only write) and referenced by `profiles.avatar_url`. An optional bio (`profiles.bio`, up to 256 chars - tightened from an initial 500 once it was actually in use) is shown on the user's public profile page.
- **Admin**: first name (4–32 chars) + optional last name (4–32 chars when given), email (valid, unique), optional phone number. Same `profiles` table and `last_name` constraint as User - there's no role-conditioned rule, so this follows User's last-name-is-optional change too.
- **Post**: belongs to a user, has a title (4–64 chars), content (16–8192 chars), up to 5 optional uploaded images (`post_images`, PNG/JPG/WEBP/GIF/AVIF, up to 5MB each), comments, and separate upvote/downvote counts (`like_count`/`dislike_count`) — the UI shows their difference as a single score, with the raw split available on hover.
- **Comments** are replies to posts, authored by other users. Deleting a comment (its own author, or an admin) soft-deletes it - content becomes `[deleted]` rather than the row being removed, so the thread's structure (replies included) stays intact.
- **Votes**: one row per (voter, post-or-comment) in `votes` with `value` of `1` or `-1`; a trigger keeps `posts.like_count`/`dislike_count` and the content author's `profiles.reputation` in sync on insert/update/delete, and blocks voting on your own content.
- **Tags**: lowercase-only, deduplicated (reuse existing tag rows instead of creating duplicates), attached to a post at creation and editable afterward via the edit-post form. Post authors manage tags on their own posts (add and remove); admins can only remove tags from any post, never add one.
- **Reputation**: a per-user score that updates automatically when a post/comment is upvoted or downvoted (and reverses when a vote is removed).
- **Badges**: auto-awarded on milestones (post count, comment count, reputation thresholds, tenure); shown next to the username on posts and comments alike, and (with their earned date) on both the own-profile page and the public per-user profile page.

Application surfaces to keep separated by access level:

- **Public part** (no auth): landing page with platform stats (user count, post count), top 10 most-commented posts, 10 most recent posts, registration/login, light/dark mode toggle.
- **Private part** (authenticated users): browse/sort/filter posts, view a single post with comments/likes/actions inline, edit profile (username is immutable after registration; optional profile photo), create posts, edit/delete only own posts and comments, comment on any post.
- **Admin part** (admin role): search users by username/email/display name, block/unblock users (blocked users cannot post or comment), delete any post, view/filter/sort all posts.

Table organization in Supabase is left to the implementation, but should reflect the entities and relationships above (users, posts, comments, tags, post_tags, votes/reputation, badges).

Pointer events (not mouse events) with `setPointerCapture` drive the drag, so panning keeps working even if the cursor leaves the viewport mid-drag.

  `PostForm` also has an "Images (`n`/`MAX_POST_IMAGES`)" field - the count lives in the label itself (`Images ({imageItems.length}/{MAX_POST_IMAGES})`), not as separate text below, and the field has no required-mark (same as Tags - it's genuinely optional, just without an "(optional)" suffix cluttering the label) - for up to `MAX_POST_IMAGES` (5) images: `src/lib/postImages.ts` has the shared constants/validation (PNG/JPG/JPEG/WEBP/GIF/AVIF, up to 5MB each, checked client-side via `validatePostImage()` and server-side by the `post-images` Storage bucket's own `file_size_limit`/`allowed_mime_types` - migration `30_post_images.sql`, same public-read/owner-write-scoped-to-their-own-folder pattern as the `avatars` bucket); the hint line under the "Add image(s)" button just states the constraint (`{ALLOWED_POST_IMAGE_LABEL} | 5MB per image`), since the count no longer needs to live there too. Each attached image is its own row in `post_images` (migration `31_post_images_multi.sql`: `post_id`, `image_url`, `position`; publicly readable, insert/delete restricted to the post's own author, insert additionally gated on `not is_blocked()` same as posts/comments - removal isn't, mirroring the vote/bookmark-removal asymmetry noted elsewhere) rather than a single `posts.image_url` column (migration 30's original design) - that let a post carry only one image, and, because attaching it after creation meant a follow-up `UPDATE` on `posts`, wrongly marked a brand-new post "(edited)" the moment an image was added (`image_url` was one of the columns `set_posts_updated_at()` watched). Moving images to their own child table fixed both problems: `PostForm` shows up to 5 thumbnails (existing images plus newly staged files, each with its own small round remove button) with an "Add image(s)" button that disables once 5 are staged, `uploadPostImage()` is a pure storage upload with no table write (author uid + a fresh random id as the path - not the post's id, since on creation there isn't one yet), and images are attached via `replacePostImages(postId, urls)` (clear-and-reattach, same strategy as `replacePostTags()`) called *after* `createPost()`/`updatePost()` - a plain insert into a separate table, so - like tags - it never touches `posts.updated_at` and never triggers "(edited)" at all, on creation or edit. A `trg_enforce_post_image_limit` trigger enforces the 5-image cap server-side too, as defense in depth alongside the client's own check. The gallery (when non-empty) renders on `PostView` via `.post-view-images`, a responsive grid between the post's content and its tags - each thumbnail is a `<button>` (not a bare `<img>`, so it's keyboard-reachable) that opens `src/components/ImageLightbox` on click, a full-screen viewer (drag to pan once zoomed, a `−`/`%`/`+` control cluster, a close button, Escape-to-close, and click-the-backdrop-to-close) for inspecting one image at a time up close - zoom state resets per image since the component isn't keyed to persist it across opens, and pan is clamped to the zoomed image's own bounds (nothing to pan at 100%, since the image is shown at its full "contain"-fit size already). Two gotchas from getting this right: the zoomed `<img>` has an inline `transform`, which (per CSS stacking rules) promotes it into the same paint layer as `position: absolute` elements with `z-index: auto` - since it's later in the DOM than the close button/zoom-controls, it was painting *over* them until they got an explicit `z-index: 1` to force them above it. And their backgrounds are a dark `rgba(0, 0, 0, 0.55)` (not the translucent *white* a typical dark-UI control would get) specifically because they sit on top of arbitrary, unknown-color user-uploaded images - a light photo would wash out white-tinted controls to the point of being unreadable, where a dark pill stays legible over any image. `ImageLightbox` and `AvatarCropper` both need pointer-drag-to-pan, so the pointer-capture/release plumbing (not the clamping math, which differs per component's own layout) is shared via `src/lib/usePointerPan.ts` - it reports each pointermove as a delta since the *previous* move (not since the drag started), so callers fold it into their own offset state with a plain functional `setOffset((current) => clampOffset(current.x + dx, ...))` update rather than snapshotting a start offset themselves.
  `ImageThumb` (inside `PostForm.tsx`, one per staged/existing image) has its own gotcha: `PostForm` rebuilds the `imageItems` array - and every `ImageItem` object in it - from scratch on every render, so a `useMemo` that depends on the `item` object itself would treat an unrelated re-render (typing in the Title field, say) as a brand new image and needlessly recreate its blob URL. The fix is depending on the stable `File` reference inside `item` instead of `item` itself.
- **Post view** (`/posts/:id`, `src/pages/PostView`, deliberately **not** auth-guarded — anyone can read a post and its comments, unlike the "Private part" grouping above, per an explicit product call): author card (avatar level with name/username, badges in their own row underneath), title/content, clickable tags (link to the equivalent search) under the content, then a `#post-vote-actions` row with the upvote/downvote arrows plus a Save/Saved bookmark button (any signed-in user, own post included; backed by the `saved_posts` table via `src/lib/savedPosts.ts` and `PostDetail.isSaved`; filled/primary-styled when saved) all on the left, and, on the right, Edit/Delete buttons for the post's own author, separated from the comments section below by a bottom border on that row. Save and Edit/Delete render as real `.button`s now (not the plain-text `.action-link` style comments still use) so they read as more prominent, deliberate actions. A blocked user can still remove an existing bookmark but can't create a new one (mirrors how vote removal, unlike casting a vote, was never gated on `is_blocked()` - see `saved_posts`' RLS policies). Both post and comments show "(edited)" next to their timestamp once their content has actually changed (not just voted on - see the `updated_at` note below). The comments section starts with the "Comments (N)" heading immediately followed by the comment composer (so leaving a comment doesn't need scrolling past the whole thread), then the comment list. Each comment shows its author's badges next to their username, can be replied to, and its own author gets Edit (inline) / Delete links. Replying to a reply doesn't create a second layer of nesting - `comments.parent_comment_id` still only ever points at a top-level comment (the schema and `notify_on_comment_insert()` trigger were never restricted to one level, but the UI deliberately keeps threads flat): `startReply()` resolves `comment.parentCommentId ?? comment.id` into `replyingToParentId`, the actual parent a submitted reply attaches to. That's kept distinct from `replyingToCommentId`, which is just wherever the "Reply" button was actually clicked (top-level or a reply) and controls where the single shared composer visually renders - `renderReplyForm(commentId)` is called after *every* comment body (top-level and each reply) and only the one matching `replyingToCommentId` renders, so the box always appears directly under whichever comment is being replied to rather than in one fixed spot per thread. `replyingToAuthor` similarly tracks the actually-clicked comment's author (not necessarily the top-level one) so the placeholder names the right person even if the prefilled `@mention` is cleared out. The textarea's caret is explicitly moved to the end of that prefilled text on open (`replyTextareaRef` + a `replySessionId` counter bumped on every "Reply" click, read by a `useEffect` that calls `.focus()`/`.setSelectionRange()`) - left alone, a freshly-focused textarea with existing content puts the caret at the very start, before the `@username`, which is wrong for a compose box meant to be typed into after the mention. Voting, commenting, replying, editing and deleting all require a signed-in, non-blocked user, enforced both client-side and via RLS/triggers (`src/lib/postDetail.ts` has the queries/mutations); signed-out visitors see "Log in to vote"/"Log in to comment" prompts instead. Deleting the post opens the shared `ConfirmDialog` and, on success, navigates to the author's own public profile page (not `/profile`, which no longer lists posts). Deleting a *comment* (own author here; any comment from the admin comments modal - see below) opens a `ConfirmDialog` ("Delete comment") rather than a native `window.confirm()` - it used to be a native confirm here too, but that blocked Claude in Chrome's browser automation (per the tool's own warning) every time it needed to verify a delete, so both paths now go through the same dialog-based flow, keyed on a `deleteCommentTarget: CommentItem | null` state (mirroring `showDeletePostConfirm`) rather than firing straight off the Delete link. It's a soft delete (content replaced with `DELETED_COMMENT_PLACEHOLDER`, `"[deleted]"`, `is_deleted` set true - see the Comments entity note above): a deleted comment keeps its author/badges/timestamp but shows the placeholder in place of its real content, in italics (`.comment-content-deleted`), and loses its Edit/Delete links - `wasEdited` also short-circuits to `false` for a deleted comment so it doesn't additionally show "(edited)" next to the placeholder. Reply stays available even on a deleted top-level comment, since the thread structure is the whole point of not hard-deleting it. Clicking "Reply" prefills the composer with `@{authorUsername} ` (that author's own username, not the viewer's) - it's plain editable text in the textarea, but once posted it's read back by `MentionText` (`src/components/MentionText`, used for both top-level and reply comment bodies, not the admin comments-moderation modal, which shows raw content on purpose) the same as any other `@username` token in the content, turning it into a link to that profile. A `#comment-{id}` hash on `/posts/:id` (as produced by a notification - see below) scrolls to and briefly highlights (`.comment-item-highlighted`, a 2.5s fade) the targeted comment once comments have finished loading; the highlight is applied via a deferred `setTimeout` rather than synchronously in the scroll effect, since `react-hooks/set-state-in-effect` (this project's stricter eslint-plugin-react-hooks v7 rule, distinct from the older `exhaustive-deps`) rejects calling a state setter directly in an effect body.
- **Notifications**: a `notifications` table (migration `33_notifications.sql`, hardened by `34_notification_fixes.sql`) is populated entirely by a `SECURITY DEFINER` trigger on `comments` insert (`notify_on_comment_insert()`, following the same bypass-RLS-to-write-another-user's-row pattern as `apply_vote_effects()`/`check_and_award_badges()`) - never written to directly from the client, which only ever reads (`"Recipients can view own notifications"`) and marks its own rows read (`"Recipients can mark own notifications read"`, backed by an `enforce_notification_restrictions()` trigger that rejects any update touching a column other than `is_read`, the same immutability-guard pattern as `enforce_profile_restrictions()`/`enforce_post_restrictions()` - added after a code-review pass found the bare RLS policy let a recipient rewrite any column of their own row). - **Storage cleanup gotcha**: deleting a DB row that referenced a Storage file (a post, a `post_images` row, a profile) never deletes the underlying file - there's no FK from `storage.objects` into `public`, so nothing cascades there, and deleting rows from `storage.objects` directly via SQL only removes the metadata row and leaves the actual file orphaned in the bucket (per Supabase's own docs - Storage objects must always go through the Storage API's `remove()`, client-side or in an Edge Function, never a raw SQL `delete`). `src/lib/storageCleanup.ts`'s `clearStorageFolder(bucket, prefix, exclude?)` lists and removes every object under a `${prefix}/` folder in one shot (paginating in batches of 100 - `list()`'s default page size - rather than a single call, so a folder with more than 100 files, e.g. a prolific poster's `post-images/{userId}/`, doesn't silently leave everything past the first page behind) - used for `avatars`/`{userId}` (on avatar replace, in `uploadAvatar()`, and on account delete, in `Profile.tsx`) and for `post-images`/`{userId}` (only on account delete, since that bucket holds images from *all* of a user's posts, not just one). Deleting a single post instead goes through `deletePostImageFiles()` in `src/lib/postImages.ts` (extracts each image's bucket-relative path from its public URL via `extractStoragePath()`, then removes just those) - `posts.ts`'s `deletePost()` calls it with the post's images fetched *before* the delete (since `post_images` rows cascade away with the post) but only *after* the delete itself succeeds, so a failed delete doesn't strand a post with broken image links. `replacePostImages()` (post editing) uses the same helper for only the subset of images that were actually removed (present before, absent from the new list) - reordering or keeping an image never touches its file, and `EditPost`'s own `handleSubmit` skips calling `replacePostImages()` at all when the final image list is identical (same URLs, same order) to what the post already had, so a title/content-only edit doesn't do a pointless `post_images` delete-and-reinsert. All of these storage cleanups are deliberately best-effort (errors aren't surfaced to the caller) - a stuck orphan file is a much smaller problem than blocking the user's actual action (deleting their post/account, changing their avatar) on a transient Storage hiccup. The `post-images` bucket's delete policy allows `is_admin()` in addition to the file's own owner (migration `32_post_images_admin_delete.sql`), since an admin deleting someone else's post from `AdminPosts` reuses this same `deletePost()`/`deletePostImageFiles()` path and needs to be able to clean up files that aren't in their own folder. Both `uploadAvatar()` and account deletion order their own writes so a failure partway through can't destroy something that was still working: `uploadAvatar()` uploads the new file and updates `profiles.avatar_url` *before* clearing out any stale previous avatar (an upload/DB failure then just leaves the old avatar in place, not the user with no avatar file at all - `clearStorageFolder()`'s `exclude` param is what lets it skip the file it just wrote), and `Profile.tsx`'s account-delete handler calls `delete_own_account()` *before* clearing the user's Storage folders (a failed RPC then leaves the account and every image intact, rather than an account that still exists but every image already wiped) - safe to reorder this way since the SQL `delete` the RPC runs never revokes the caller's JWT, so it's still valid for the Storage calls that follow even though the row it was authenticated against is already gone.
- **`updated_at` gotcha**: `posts`/`comments` each have their own trigger (`set_posts_updated_at`/`set_comments_updated_at`) that only bumps `updated_at` when the user-editable columns actually change (title/content for posts, content for comments) - NOT the generic shared `set_updated_at()` used by `profiles`. If you add a new mutable column to either table, make sure it's covered by that same trigger's condition, or actions that touch it (like votes touching `like_count`) will start silently marking things as edited - a first cut of the post-images feature learned this the hard way (see the Create/edit post note above): it originally stored a single `image_url` *column* on `posts` (migration 30) and added it to this trigger's condition so replacing it would count as an edit, like title/content - but attaching it via a follow-up `UPDATE` right after a post's `INSERT` then wrongly marked brand-new posts "(edited)" too. Moving images to their own `post_images` child table (migration 31) sidestepped the whole class of bug: a child-table insert/delete never touches `posts.updated_at` at all, the same as tags.
- **`parent_comment_id` immutability gotcha**: `enforce_comment_parent_same_post()` blocks retargeting a reply to a *different* specific parent (or attaching one to a previously top-level comment), but deliberately allows it to become `null` - that's what the `ON DELETE SET NULL` cascade does when a comment's parent is deleted (orphaning the reply instead of destroying it), and that cascade fires through the same BEFORE UPDATE trigger. This no longer fires during normal use now that deleting a single comment is a soft delete (see the Comments entity note above) rather than an actual `DELETE` - a comment's row, and so its replies' `parent_comment_id`, only really goes away via the `posts`→`comments` cascade when the whole post is deleted, which removes the entire tree together and so never needs to orphan anything. The trigger (and this guard) still exist as a safety net for that path and for any future direct hard-delete - if you tighten this guard again, keep the null case working.
- **Button chrome gotcha**: the shared `.button`/`.button.primary`/`.button.danger` classes live in `src/pages/Home/Home.css` (not ideal, but that's where they've always been, and every page's CSS bundles into one global stylesheet regardless of which component imports it, since nothing here is code-split). A plain `<button className="button">` (no `.primary`/`.danger`) needs the `button.button` background rule there too: `:root` sets `color-scheme: light dark`, so an unstyled native `<button>` gets the browser's own dark or light chrome based on the OS preference, not this app's manual theme toggle - the two can disagree (e.g. OS dark + app toggled to light) and produce unreadable text. `<a className="button">` doesn't need this since anchors don't get that native chrome.
- **Shared bits**: `PasswordInput` (`src/components/PasswordInput`) gives every password field a show/hide eye-icon toggle. `formatDateTime()` (`src/lib/formatDate.ts`) renders timestamps in the viewer's own timezone, year down to minutes. `src/lib/publicProfiles.ts` has the shared `public_profiles()` batching helper used by posts/postDetail/search. The page always reserves a vertical scrollbar (`overflow-y: scroll` on `:root`) so short pages don't shift width relative to long ones.
